# 로컬 LLM 모델 비교 평가 결과 (2026-10-15)

환경: Apple M3, 8 GB, LM Studio 0.4.26, GGUF Q4_K_M, temperature 0, JSON 스키마 강제, reasoning_effort=none.
평가 문장 50개(`cases.jsonl`, 유형 10가지). 지표 정의는 `README.md` 3절.

| 단계 | Qwen3 4B Instruct 2507 | Kanana 2 3B | Gemma 4 E2B |

- 50문장에서 1~2건 차이는 실행 간 편차 안에 있다 (프롬프트가 바뀌면 temperature 0이어도 출력이 달라진다).
- Qwen의 응답 시간은 v1(14.4 s)보다 느린데, 평가 중 메모리 스왑이 5 GB를 넘었던 영향이다. 논문용 속도는 다른 앱을 닫고 다시 재야 한다.
- v2 행은 실행 중 고친 검사 버그("1시간"→60분 변환값을 뺌)를 반영해 같은 LLM 출력을 재채점한 값이다.
- 마지막 행은 LLM을 다시 부르지 않고 v3 출력을 새 온톨로지로 재채점한 값이다. 온톨로지에 PGMEA·NMP 용매와
  코팅 재료 클래스(`vd:Coating`: PEDOT:PSS, 포토레지스트)를 더하자 세 모델 공통 실패였던
  "PEDOT:PSS 박막→기판", "PGMEA→기판"이 코드 수정 없이 사라졌다. 이에 따라 `unknown-solvent` 사례는
  유형을 '미등록 용어'에서 '용어 연결'로 바꿨다(문장·정답은 그대로).

v4는 채팅에 의도 분류(조건 입력·수정·질문·기타)와 질문에 대한 근거 답변을 넣은 버전이다. 평가 문장에
질문·수정·잡담 7개를 더해 57개가 됐고, 의도 정답을 항목 하나로 채점한다. 세 모델 모두 의도 7개 중 7개를 맞혔다
(Qwen은 기존 문장 "지난번이랑 같은 조건으로 해줘"를 잡담이 아닌 질문으로 봤다). 의도 라벨이 없는 원래 문장 47개만 보면
Qwen 45/47, Kanana 36/47, Gemma 45/47로 v3과 같은 수준이다. 즉 프롬프트에 의도 규칙을 더해도 추출은 나빠지지 않았다.
v4 실행 중 다른 앱을 모두 닫아 응답 시간이 v3보다 빨라졌다(Gemma 10.5 s).

v4에서 평가가 잡아낸 설계 결함 두 가지와 수정:
- 질문 속 이름("이 조건이면 PET 괜찮아?")을 온톨로지 사전이 기판 값으로 채워 초안이 다시 만들어졌다 →
  온톨로지가 채운 값은 의도 판단에서 제외.
- 질문이 현재 값을 그대로 인용하면("왜 1.333 kPa로 잡았어?") LLM이 그 숫자를 뽑아 수정으로 처리됐다 →
  초안과 같은 값은 "바뀐 값"으로 보지 않음. 반대로 LLM이 진술("시편 번호 W-03 준비됐어")에 질문 표시를 붙여
  값이 버려지는 일도 있어, 이름만 있을 때는 문장의 의문 표현을 LLM 표시보다 우선한다.

## v5: 개발자가 만든 질문으로 돌린 학습 루프 (2026-10-16)

가중치 학습이 아니라, 실제 연구실에서 나올 법한 문장 28개를 새로 만들어 모델에 넣고 틀린 데를 프롬프트·온톨로지·
코드로 고치는 반복이다. Gemma 기준선 19/28 → 수정 후 28/28. 질문이 드러낸 빈틈과 수정:

| 드러난 문제 | 예 | 수정 |
|---|---|---|
| 상대 변경을 절대값으로 | "온도 10도 올려줘" → 10°C | 초안이 있고 숫자 하나가 동사 앞에 오면 더하거나 뺀다. 로/까지가 붙으면 절대값. "절반으로" 같은 배수도 처리 |
| 허락 질문이 초안을 바꿈 | "200도까지 올려도 돼?" → 200°C로 변경 | 초안은 두고 그 값으로 SHACL 검사만 해서 답한다 |
| 재료·진행 질문에 초안 근거만 반복 | "PET 최대 온도가 몇 도야?", "얼마나 걸려?" | 온톨로지 물성, 최대 소요 시간, 승인 절차로 답한다. 초안 없이도 됨 |
| 공정 순서 환각 | "건조 후 식혀서"의 '후' → heat_first | 온톨로지가 순서 표현을 찾았을 때만 받는다. 표현 사전 30개로 확장 |
| 최소/최대 유지 시간 혼동 | "2시간 30분 유지" → 최소 유지 시간 | '최소'라는 말이 없으면 최대 유지 시간. 두 숫자의 환산 합(150분)도 근거로 인정 |
| 수정 지시에서 값 누락 | "압력은 0.5 kPa 낮춰" → 값 없음 | 항목 하나 + 숫자·단위 하나뿐이면 코드가 온톨로지 단위로 직접 읽는다 |
| 같은 숫자를 두 항목에 | "판정 구간 1분" → 최소 유지 시간 1분도 | 숫자 앞에 이름이 붙은 항목만 남긴다 |

85문장 전체를 저메모리 설정(문맥 4096, 동시 처리 1)으로 돌려 85/85, 환각 0, 응답 중앙값 11.6 s(최대 14.5 s).
주의: 이 85문장은 개발 중 실패를 보고 규칙을 만든 문장이므로 과적합 위험이 있다. 논문에서는 팀의 실제 계획서
문장을 따로 모아 **한 번도 보지 않은 시험 세트**로 보고해야 한다. Qwen·Kanana는 v5 세트로 아직 돌리지 않았다.
평가 중 메모리가 부족해 컴퓨터가 느려지는 문제는 `--resume`(사례마다 저장)과 모델 적재 옵션으로 대응했다.

"검사 제외 환각"과 "환각"의 차이가 근거 검사의 기여, "보완 제외 정확도"와 "필드 정확도"의 차이가 온톨로지 사전 보완의 기여다.

## 무엇이 효과를 냈나

1. **프롬프트 지침·예시**: Kanana의 검사 전 환각 162 → 60. 예시 하나만 있을 때 작은 모델은 예시 값을 그대로 베꼈다.
2. **부정문의 함정**: v2에서 "'시편', 'sample', 재료 이름은 시편 ID가 아니다"라고 쓰자 Qwen이 오히려 `sampleId: "MeOH"`, `"시편"`을 넣었다(환각 10 → 9에 그침). v3에서 지침을 모두 긍정문으로 바꿨다.
3. **근거 검사**: 문장에 없는 숫자·이름, 종류가 틀린 이름(기판 칸의 용매), 일반 명사("시편"), 형식이 틀린 ID, 문장 표현과 어긋난 공정 순서, 요청 문장을 통째로 옮긴 메모를 뺀다. Kanana 환각 61 → 6, Qwen 8 → 4.
4. **온톨로지 보완**: "최대 진공"→펌프 최저 압력, 문장에서 찾은 용매·기판·순서로 LLM이 놓친 항목을 채운다. 정확도 +2~3%p.

## 결론

- **기본 모델: Gemma 4 E2B** (55/57, 환각 1, Apache 2.0, 약 10~15 s). Qwen3 4B가 근소한 차이로 다음.
- 질문("왜?")에는 LLM이 답을 쓰지 않는다. 단위 변환·용어 연결·기본값·규칙 결과·온톨로지 지식을 코드가 엮어
  설명하므로 지어낼 수 없다. 온톨로지가 설명 가능성(explainability)을 제공하는 사례다.
- Kanana 2 3B는 한국어 특화라도 이 역할(구조화 추출)에는 부족하다. 다만 온톨로지+검사 층이 약한 모델을 0 → 34/50까지 끌어올린다는 점이 논문의 핵심 근거가 된다.
- 50문장은 개발자가 쓴 것이다. 팀의 실제 계획서 문장을 `cases.jsonl`에 보태야 한다.
