# 공정 자동화 AI — 로컬 LLM + 온톨로지 (진공 가열 건조)

> 2026 반도체 캡스톤디자인 2 (강남대학교 VTR Lab) · 작성자: 조원곤 (AI·소프트웨어 파트) · 논문용 알고리즘 의사코드는 `paper/`에 있습니다.

실험 계획을 양식이나 채팅으로 입력하면 레시피로 바꾸고, 작업자가 승인하면 장비가 자동으로 공정을 진행합니다.
AI는 **이 PC에서 도는 로컬 LLM**이고, 장비·재료 지식과 규칙은 **온톨로지**에 있습니다. 외부로 나가는 데이터가 없습니다.

```
계획 입력 ─► 로컬 LLM ─► 온톨로지 ─────────────► 작업자 승인 ─► 공정 제어기 ─► 아두이노
 양식/채팅    값 추출     용어 연결·단위 변환·         콘솔 화면       상태 머신·
                          SHACL 규칙 검증·지식 안내                    안전 인터락
                                   ▲                                       │
                                   └──────── 실행 이력(PROV-O) 누적 ◄──────┘
```

공정 순서: **문 닫기 → 진공 배기 → 승온 → 건조(포토다이오드로 종료점 감시) → 냉각 → 벤트 → 문 열기**

온톨로지가 처음이라면 [ontology/README.md](ontology/README.md)부터 읽으세요.

## 역할 분담

| 누가 | 하는 일 | 파일 |
|---|---|---|
| 로컬 LLM | 문장에서 값과 단위를 적힌 그대로 뽑기 (정보 추출만) | `llm.py`, `planner.py` |
| 온톨로지 | 추출 항목 정의와 항목별 추출 지침, 용어 연결(IPA→이소프로판올), 단위 변환(Torr→kPa), 검증 규칙 23개, 물성 안내, 실행 이력 | `ontology/`, `knowledge.py` |
| 코드 | 근거 검사(문장에 없는 값·종류가 틀린 이름 빼기), 대화 상태, 필수값 확인, 기본값, 답변 문구, 공정 제어 | `planner.py`, `controller.py` |
| 작업자 | 레시피 검토와 승인 | 콘솔 화면 |

채팅에서 할 수 있는 말:

| 종류 | 예 | 동작 |
|---|---|---|
| 조건 입력 | "IPA 시편 5 kPa 80도" | 초안을 만들거나 채웁니다 |
| 값 수정 | "온도 90도로", "온도 10도 올려줘", "압력 절반으로" | 초안을 고치고 "바꿨어요: 80 → 90 °C"로 알립니다. 숫자 뒤에 로/까지가 없으면 상대 변경입니다 |
| 근거 질문 | "왜 압력을 그렇게 잡았어?", "기본값은 뭘 바탕으로?" | 단위 변환·용어 연결·기본값 근거·규칙 검사·물성으로 설명합니다 |
| 가정 질문 | "200도까지 올려도 돼?", "왜 150도는 안 돼?" | 초안을 바꾸지 않고 그 값으로 규칙 검사만 해서 답합니다 |
| 재료 질문 | "PET 최대 온도가 몇 도야?", "IPA랑 에탄올 중 뭐가 빨리 말라?" | 온톨로지의 물성으로 답합니다. 초안이 없어도 됩니다 |
| 진행 질문 | "얼마나 걸려?", "다음에 뭐 해?" | 최대 소요 시간, 승인 절차와 공정 순서를 안내합니다 |
| 그 외 | "공정 시작해", "처음부터" | 채팅으로는 공정을 시작하지 않는다고 안내하고 승인 화면으로 보냅니다 |

답은 모두 LLM이 아니라 코드가 실행 중 생긴 정보와 온톨로지로 만들므로 지어낼 수 없습니다.

**쓸수록 나아지는 방식 (작업자 수정 학습).** 모델 가중치는 고정이고 쓰면서 스스로 배우지 않습니다. 대신
AI 초안을 검토 화면에서 고쳐 승인하면 (대화 문장 → 승인된 값) 쌍이 `examples/examples.jsonl`에 항상 쌓입니다.
이 기록은 `python3 -m process_ai.examples export-cases`로 평가 사례(한 번도 보지 않은 시험 세트)로 내보낼 수 있고,
수백 개가 쌓이면 LoRA 파인튜닝 자료가 됩니다.

쌓인 기록을 프롬프트에 되먹이는 기능(`PROCESS_FEWSHOT_K`, 비슷한 과거 문장과 정답을 이전 대화 턴으로 넣기)도
있지만 **기본은 꺼져 있습니다.** Gemma 4 E2B로 시험해 보니 비슷한 문장을 보여 주면 새 문장의 값(예: "90도로 건조"의
90도)을 빼 버리는 일이 있었습니다(예시 없음·예시 2개일 때는 정상, 1개일 때 누락). 켜면 필수값을 놓쳤을 때 예시 없이
다시 읽는 안전장치가 작동하지만, 평가로 득실을 확인한 뒤 쓰는 것이 맞습니다. 어떤 기록을 참고했는지는 채팅 메모에 표시됩니다.
문장의 종류는 LLM이 표시하고(`intent`), 바뀐 숫자가 뽑혔으면 LLM이 뭐라 했든 수정으로,
값이 없고 의문 표현이 있으면 질문으로, 숫자가 있어도 "돼?"처럼 허락을 묻는 말이면 가정 질문으로 봅니다.
공정 순서는 온톨로지가 문장에서 순서 표현("예열 후 진공", "진공 먼저")을 찾았을 때만 받습니다.

작은 모델(3~4B)은 계산과 판단에서 실수가 잦습니다. 그래서 LLM에게는 추출만 맡기고,
출력을 JSON 스키마로 강제하고, 모든 결과를 온톨로지 규칙으로 다시 검사합니다.
LLM이 낸 숫자와 이름은 원문에 실제로 있는지도 확인합니다(근거 검사). 프롬프트 예시의 값을 베끼거나,
기판 칸에 용매 이름이나 "시편" 같은 일반 명사를 넣거나, 요청 문장 전체를 메모로 옮기는 실수를
이 단계에서 걸러내고, 뺀 값은 작업자에게 알립니다. 무엇이 일반 명사이고 시편 ID가 어떤 형식인지는
온톨로지(`vd:GenericTerm`, `vd:valuePattern`)에 있습니다.
장비 한계값(최대 온도, 최저 압력 등)은 코드에 없고 `ontology/vd-equipment.ttl`에만 있습니다.

## 1. 로컬 LLM 준비 (8GB 메모리 기준)

**LM Studio (그래픽 화면, 추천)**
1. [lmstudio.ai](https://lmstudio.ai)에서 Mac(Apple Silicon)용을 받아 설치합니다.
2. 모델 검색에서 4B 이하 모델을 받습니다. 메모리에 맞는지 화면에 표시됩니다.
   후보: Qwen3 4B, Gemma 3 4B, EXAONE 3.5 2.4B(한국어 강점), Llama 3.2 3B
3. 개발자(Developer) 화면에서 모델을 불러오고 서버를 켭니다. 기본 주소는 `http://localhost:1234`입니다.
4. 콘솔 상단 배지가 초록색 "로컬 LLM: 모델 이름"으로 바뀌면 연결된 것입니다.

**Ollama (터미널)**

```bash
brew install ollama
ollama pull qwen3:4b
ollama serve
```

Ollama를 쓸 때는 서버를 띄우기 전에 `PROCESS_LLM_URL=http://localhost:11434/v1`로 설정하세요.

**8 GB 메모리에서 느려질 때.** 모델(약 4 GB)과 다른 앱이 메모리를 나눠 쓰면 스왑이 생겨 컴퓨터 전체가 느려집니다.
- 평가나 시연 전에 브라우저·메신저 등 다른 앱을 닫으세요.
- 모델은 문맥 길이를 줄이고 동시 처리 1개로 올리세요(기본 8192·4개보다 메모리를 덜 씁니다). 10분 쉬면 자동으로 내려갑니다.
  ```bash
  lms load google/gemma-4-e2b -c 4096 --parallel 1 --ttl 600
  ```
- 다 쓰면 `lms unload --all`로 내리세요. 콘솔 서버는 다음 채팅에 모델을 다시 올립니다.
- 긴 평가는 `--resume`을 붙이면 사례마다 저장하므로, 느려지면 중단했다가 나중에 이어서 돌릴 수 있습니다.

어느 모델이 나은지는 아래 평가 도구로 직접 비교해서 고르세요. 모델마다 라이선스가 다르니
(예: EXAONE은 비상업 연구용) 기업 환경을 가정한다면 상업 이용 가능 여부도 함께 확인하세요.

## 2. 실행

저장소 폴더 안에서 (폴더 이름이 `process-ai`든 `process_ai`든 상관없습니다):

```bash
pip3 install -r requirements.txt
python3 start.py
```

브라우저에서 http://localhost:8100 을 엽니다. 기본은 **시뮬레이터 모드**(20배속)라서 장비 없이 전체 공정을 돌려볼 수 있습니다.
로컬 LLM 없이도 양식 입력, 검증, 공정 실행은 모두 동작합니다.

**로컬 LLM을 돌릴 수 없는 PC에서 채팅까지 써 보려면** (메모리 부족, LM Studio 미설치, 클라우드 등):

```bash
PROCESS_LLM_URL=rules python3 start.py
```

LLM 대신 `rules.py`의 **규칙 기반 추출기**가 문장에서 값을 뽑습니다 (온톨로지의 단위·항목·재료 사전으로 정규식 매칭).
화면 배지가 노란색 "규칙 기반 추출기 (로컬 LLM 없음)"으로 바뀝니다. 정해 둔 표현만 읽으므로 처음 보는 말투나 긴 문단은
LLM보다 많이 놓칩니다. 자동으로 켜지지 않고 주소를 `rules`로 적었을 때만 씁니다. 논문에서는 "LLM 없는 비교 기준"으로 쓸 수
있습니다 (`python3 start.py eval --url rules`).

`python3 -m uvicorn process_ai.server:app --port 8100`처럼 모듈로 실행하려면 폴더 이름이 `process_ai`여야 하고
그 상위 폴더에서 실행해야 합니다. `start.py`는 이 조건 없이 돌아갑니다. 테스트는 폴더 안에서 `python3 -m pytest`.

| 환경 변수 | 기본값 | 설명 |
|---|---|---|
| `PROCESS_LLM_URL` | `http://localhost:1234/v1` | 로컬 LLM 서버 (OpenAI 호환 API). `rules`면 LLM 없이 규칙 기반 추출기 |
| `PROCESS_LLM_MODEL` | (비움) | 비우면 서버에 올라온 첫 모델을 씀 |
| `PROCESS_LLM_TIMEOUT` | `120` | 응답 대기 시간(초) |
| `PROCESS_LLM_REASONING` | `none` | 추론형 모델(Gemma 4 등)의 "생각 과정"을 끔. 값 추출에는 필요 없고 응답만 몇 배 느려짐. 빈 값이면 보내지 않음 |
| `PROCESS_DRIVER` | `sim` | `arduino`로 바꾸면 실제 장비에 연결 |
| `PROCESS_SERIAL_PORT` | `/dev/tty.usbmodem1101` | 아두이노 포트 (`ls /dev/tty.usb*`로 확인) |
| `PROCESS_SIM_SPEED` | `20` | 시뮬레이터 배속 |
| `PROCESS_EQUIPMENT` | `Chamber01` | 온톨로지의 장비 개체 이름 |

VS Code로 이 폴더를 열고 내장 터미널에서 위 명령을 실행하면 됩니다. `.ttl` 파일을 편하게 보려면
확장 마켓플레이스에서 "Turtle"이나 "RDF"로 검색해 문법 강조 확장을 설치하세요.

## 3. 모델 비교 평가

```bash
python3 start.py eval --model qwen3-4b --model gemma-3-4b-it
python3 start.py eval --url rules        # 규칙 기반 추출기 (LLM 없는 비교 기준)
```

`evaluation/cases.jsonl`의 계획서 문장 50개를 각 모델에 넣고 정답과 비교합니다.
문장마다 유형(`category`)이 붙어 있어 단위 변환, 용어 연결, 후속 답변 등 유형별로도 결과가 나옵니다.
모델 이름은 LM Studio나 Ollama 화면에 보이는 그대로 적으세요. `--model`을 빼면 서버에 올라온 모델 하나를 평가합니다.

| 지표 | 뜻 |
|---|---|
| 필드 정확도 | 정답 항목 중 맞게 뽑은 비율 (단위 변환 후 1% 이내) |
| 환각 | 문장에 없는데 채운 항목 수. 안전과 직결되므로 0이어야 합니다 |
| 온톨로지 보완 | LLM이 놓친 것을 온톨로지 사전이 채운 횟수 |
| 평균 응답 | 문장 하나 처리 시간. 모델 적재 시간이 섞이지 않게 한 번 미리 부른 뒤 잽니다 |
| 보완 제외 정확도 | 같은 LLM 출력에서 온톨로지 사전 보완만 빼고 다시 채점한 정확도. 필드 정확도와의 차이가 온톨로지의 기여분입니다 |
| 검사 제외 환각 | 같은 LLM 출력에서 근거·종류 검사만 빼고 센 환각 수. 환각과의 차이가 검사가 막은 수입니다 |

`--tag v2`처럼 실험 이름을 붙이면 결과 파일 이름에 들어갑니다. `--resume`을 붙이면 사례마다
`results/partial-<tag>-<model>.jsonl`에 저장하고, 중단 뒤 같은 명령을 다시 실행하면 이어서 돌립니다. 비교 실험 두 가지(보완 제외, 검사 제외)는
LLM을 다시 부르지 않고 같은 출력을 다시 채점해서 구하므로 시간이 더 들지 않습니다.

결과는 `evaluation/results/`에 저장됩니다. 실제 계획서 문장을 `cases.jsonl`에 계속 추가해 가며 평가하세요.

## 구성

| 파일 | 역할 |
|---|---|
| `ontology/` | 온톨로지(개념·장비·재료)와 SHACL 규칙. [입문서](ontology/README.md) |
| `knowledge.py` | 온톨로지 적재, 용어 연결, 단위 변환, 검증, 지식 안내, 실행 이력 그래프 |
| `llm.py` | 로컬 LLM 클라이언트 (LM Studio, Ollama, llama.cpp, vLLM 공통) |
| `rules.py` | 규칙 기반 추출기. LLM을 돌릴 수 없는 PC용 대체 추출기이자 논문의 LLM 없는 비교 기준 (`PROCESS_LLM_URL=rules`) |
| `start.py` | 실행 스크립트. 폴더 이름과 관계없이 서버·평가를 띄움 |
| `planner.py` | 채팅 → 레시피 초안 |
| `controller.py` | 공정 상태 머신, 안전 인터락, 실행 기록 |
| `endpoint.py` | 포토다이오드 신호로 건조 종료점 판정 |
| `drivers.py`, `simulator.py` | 아두이노 시리얼 드라이버, 가상 챔버 |
| `server.py`, `static/index.html` | API 서버와 운영 콘솔 |
| `examples.py`, `examples/` | 작업자가 승인한 (문장 → 값) 기록과 프롬프트 되먹이기 |
| `evaluation/` | 모델 비교 평가 |
| `firmware/chamber_controller/` | 아두이노 펌웨어 |
| `runs/<실행ID>/` | 실행마다 레시피, 센서 기록(CSV), 이벤트, 결과 요약 |

## 실제 장비에 연결하기 전에 할 일

1. `ontology/vd-equipment.ttl`의 한계값을 실제 부품 사양으로 바꾸고 `python3 -m process_ai.knowledge check`로 확인합니다.
2. `ontology/vd-materials.ttl`의 기판 최대 사용 온도(현재 예시값)와 용매 물성을 데이터시트·SDS로 확인합니다.
3. 펌웨어의 핀 번호, 압력 센서 변환식(`adcToKpa`), 릴레이 극성(`RELAY_ON`), PID 계수를 배선과 센서에 맞게 고칩니다.
   펌웨어는 이 PC에서 컴파일해 보지 않았습니다. Arduino IDE에서 MAX6675 라이브러리를 설치하고 빌드하세요.
4. 히터 전원에 **하드웨어 과열 차단 장치**(서모스탯, 온도 퓨즈)를 둡니다. 소프트웨어 인터락만으로는 부족합니다.
5. 실제 시편으로 포토다이오드 신호를 기록해 보고 `stable_window_s`, `stable_band_pct` 기본값을 정합니다.

## 안전 동작

비상 정지 조건: 최대 온도 초과, 목표 온도 대비 과열, 공정 중 문 열림, 단계별 제한 시간 초과,
센서 읽기 3회 연속 실패, 장비 명령 실패, 작업자 비상 정지 버튼.

비상 정지 시 히터와 펌프를 끄고 벤트를 엽니다. **문은 닫힌 채로 둡니다.** 온도가 내려간 뒤
콘솔의 "안전 개방" 버튼으로 엽니다.

펌웨어도 따로 막습니다: 3초 통신 두절 시 히터·펌프 정지(워치독), 과열 차단, 열전대 단선 감지, 진공 중 문 열기 거부.
